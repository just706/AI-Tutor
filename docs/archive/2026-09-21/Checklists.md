# AI Tutor 开发检查清单

## 1. 文档目标

本文档用于约束 AI Tutor 项目后续开发过程，作为开发前、开发中、完成前的检查边界清单。

目标是减少以下问题：

- 开发范围失控。
- 修改无关代码。
- 忘记权限校验。
- 忘记用户数据隔离。
- 数据库和接口文档不同步。
- AI 调用缺少失败处理。
- RAG 检索不到资料时编造回答。
- 功能完成但缺少验证。

使用方式：

- 每次开始新任务前，先检查“开发前检查”。
- 修改代码时，按对应模块检查。
- 任务完成前，必须执行“完成前检查”。

## 2. 开发前检查

开始任何开发任务前，先确认以下事项：

- [ ] 是否已经阅读 `CLAUDE.md`？
- [ ] 是否明确当前开发阶段？
- [ ] 是否明确本次任务的目标？
- [ ] 是否明确本次任务的验收标准？
- [ ] 是否确认本次任务属于 MVP，还是属于后续阶段？
- [ ] 是否确认哪些文件需要修改？
- [ ] 是否确认哪些文件不应该修改？
- [ ] 是否确认是否需要同步更新文档？
- [ ] 是否存在不确定需求？如果存在，是否已经提问或列明假设？
- [ ] 是否确认不会顺手开发用户没有要求的额外功能？

相关文档优先阅读顺序：

```text
CLAUDE.md
  ↓
docs/Checklists.md
  ↓
docs/Backend-Plan.md 或后续 Frontend-Plan.md
  ↓
docs/API.md
  ↓
docs/Database.md
  ↓
docs/AI-Design.md
```

## 3. 范围边界检查

每次开发前需要确认本次任务是否越界。

- [ ] 当前任务是否只处理用户明确要求的内容？
- [ ] 是否避免实现未要求的扩展功能？
- [ ] 是否避免提前开发后续阶段功能？
- [ ] 是否避免引入不必要的新依赖？
- [ ] 是否避免大范围重构已有正常代码？
- [ ] 是否避免修改无关格式、命名或注释？
- [ ] 如果发现无关问题，是否只记录提醒，而不是直接修改？

对应阶段开始前默认不提前做：

- [ ] 不提前开发 RAG 知识库。
- [ ] 不提前开发 AI Agent。
- [ ] 不提前开发复杂学习分析。
- [ ] 不提前开发前端页面。
- [ ] 不开发编程题自动判题。
- [ ] 不开发多模型自动调度。

## 4. 代码修改检查

修改代码时必须坚持精准局部修改。

- [ ] 是否只修改完成任务所需的文件？
- [ ] 每一处改动是否都能对应用户需求？
- [ ] 是否遵循项目已有包结构和命名风格？
- [ ] 是否没有顺手重构相邻代码？
- [ ] 是否没有删除原本就存在的无关废弃代码？
- [ ] 是否清理了本次修改产生的无用导入、变量或方法？
- [ ] 是否避免过早抽象和过度封装？
- [ ] 是否没有硬编码密钥、密码、Token 或用户隐私数据？

## 5. 后端接口检查

开发或修改后端接口时，需要检查：

- [ ] 是否使用统一响应格式 `Result<T>`？
- [ ] 是否使用统一错误码？
- [ ] 是否进行了必要参数校验？
- [ ] 是否处理参数为空的情况？
- [ ] 是否处理资源不存在的情况？
- [ ] 是否处理无权限访问的情况？
- [ ] 是否避免直接返回数据库实体中的敏感字段？
- [ ] 是否使用 DTO 接收请求参数？
- [ ] 是否使用 VO 返回前端数据？
- [ ] 是否更新 `docs/API.md`？

需要登录的接口还要检查：

- [ ] 是否校验 JWT Token？
- [ ] 是否从 Token 获取当前用户 ID？
- [ ] 是否禁止前端传入任意 `user_id` 操作数据？
- [ ] 是否校验数据是否属于当前用户？
- [ ] 未登录时是否返回 `401`？
- [ ] 无权限时是否返回 `403` 或资源不存在？

## 6. 用户认证检查

开发注册、登录、用户信息相关功能时，需要检查：

- [ ] 注册时是否校验用户名不能为空？
- [ ] 注册时是否校验密码不能为空？
- [ ] 注册时是否校验用户名唯一？
- [ ] 密码是否使用 BCrypt 加密？
- [ ] 数据库是否只保存 `password_hash`？
- [ ] 登录失败时是否避免提示过细导致账号枚举？
- [ ] 登录成功是否返回 Token 和必要用户信息？
- [ ] 接口响应是否不包含密码字段？
- [ ] 日志中是否不打印密码？
- [ ] 用户被禁用时是否阻止登录？

## 7. 数据库变更检查

新增或修改数据库表、字段、索引时，需要检查：

- [ ] 是否已经确认该表或字段属于当前阶段？
- [ ] 字段命名是否使用下划线风格？
- [ ] 主键是否明确？
- [ ] 是否需要 `create_time` 和 `update_time`？
- [ ] 高频查询字段是否需要索引？
- [ ] 用户数据表是否包含 `user_id` 用于数据隔离？
- [ ] 是否避免明文保存密码？
- [ ] 是否避免把向量数据直接塞进普通业务表？
- [ ] 枚举值是否在文档中说明？
- [ ] 是否更新 `docs/Database.md`？

Personal Graph 数据变更还要检查：

- [ ] 节点是否只在同一 `user_id`、`document_id` 范围内按规范化名称去重？
- [ ] 关系端点是否均属于当前用户和同一来源文档？
- [ ] 发布是否幂等，并在新发布时替换同文档旧结果？
- [ ] 文档重新处理或删除时，是否清理关联 extraction、节点和关系？
- [ ] 是否确保不会写入 `knowledge_point` 或 `knowledge_map_dependency`？

涉及用户数据的表，必须检查：

- [ ] 是否能通过当前登录用户限制访问范围？
- [ ] 是否能防止用户查询或修改他人数据？
- [ ] 删除或修改数据时是否校验数据归属？

## 8. AI 调用检查

开发或修改 AI 功能时，需要检查：

- [ ] AI 调用是否经过统一 AI 服务层？
- [ ] 是否没有在业务代码中硬编码 API Key？
- [ ] 模型名称是否通过配置管理？
- [ ] Prompt 是否明确 AI 角色？
- [ ] Prompt 是否包含必要学生档案？
- [ ] Prompt 是否明确输出要求？
- [ ] Prompt 是否限制不要编造无依据内容？
- [ ] 是否处理 AI 调用超时？
- [ ] 是否处理 AI 调用失败？
- [ ] 是否记录 AI 调用日志？
- [ ] 是否更新 `docs/AI-Design.md`？

结构化候选输出还要检查：

- [ ] 是否对 AI JSON、字段类型、置信度、关系类型、端点和自环进行服务端校验？
- [ ] 是否仅接受模型引用的、当前批次实际提供的 chunk 编号？
- [ ] `snippet` 是否由服务端从已验证 chunk 生成，而不是信任模型返回的引用文本？
- [ ] 解析或语义校验失败时，是否标记 extraction 为失败且不发布个人图谱？

AI 聊天接口额外检查：

- [ ] 是否保存用户消息？
- [ ] 是否保存 AI 回复？
- [ ] 是否读取最近上下文但避免无限增长？
- [ ] 是否校验会话属于当前用户？
- [ ] AI 失败时是否返回友好错误？

## 9. RAG 检查

RAG 阶段开发前，需要确认当前阶段是否允许开发 RAG。

MVP 阶段检查：

- [ ] 是否确认不实现实际 RAG 流程？
- [ ] 是否避免提前引入复杂向量数据库代码？
- [ ] 是否只在文档和架构中保留扩展方向？

RAG 阶段开发时，需要检查：

- [ ] 是否明确 LangChain4j 只负责流程编排？
- [ ] 是否明确向量数据库负责向量存储和检索？
- [ ] 是否明确 MySQL 只保存文档元数据和切片关联？
- [ ] 是否限制用户只能检索自己的文档或授权公共资料？
- [ ] 是否处理文件上传大小和类型限制？
- [ ] 是否记录文档处理状态？
- [ ] 是否处理文档解析失败？
- [ ] 资料不足时是否明确提示无法基于资料回答？
- [ ] AI 是否避免编造资料来源？
- [ ] 是否返回可追踪的来源信息？
- [ ] 是否更新 `docs/AI-Design.md` 和 `docs/API.md`？

## 10. 前端开发检查

前端开发阶段需要检查：

- [ ] 是否已有或需要补充 `docs/Frontend-Plan.md`？
- [ ] 页面是否对应 PRD 和 API 文档？
- [ ] 是否统一封装请求方法？
- [ ] 是否统一携带 Token？
- [ ] 是否处理未登录跳转？
- [ ] 是否处理接口错误提示？
- [ ] 是否处理加载状态？
- [ ] 是否处理空数据状态？
- [ ] AI 回答是否支持 Markdown 展示？
- [ ] 是否避免为了视觉效果引入过重依赖？

Personal Graph 前端还要检查：

- [ ] 是否在抽取中展示稳定的加载状态并禁止重复触发？
- [ ] 是否展示抽取失败、无候选和未发布个人图谱的空状态？
- [ ] 审核区是否同时展示候选、置信度和 chunk 证据？
- [ ] 发布成功后是否刷新 Personal Graph，且 Master Graph 不受影响？

## 11. 文档同步检查

开发过程中如果发生以下变化，必须同步文档：

- [ ] 新增或修改接口时，更新 `docs/API.md`。
- [ ] 新增或修改表结构时，更新 `docs/Database.md`。
- [ ] 修改 AI 调用、Prompt、模型配置时，更新 `docs/AI-Design.md`。
- [ ] 修改模块结构或技术选型时，更新 `docs/Architecture.md`。
- [ ] 修改阶段计划或开发顺序时，更新 `docs/Development.md` 或 `docs/Backend-Plan.md`。
- [ ] 修改部署方式、端口、环境变量时，更新 `docs/Deployment.md`。
- [ ] 新增大模块时，评估是否需要新增独立计划文档。

文档同步原则：

- [ ] 文档不能声称已完成实际尚未实现的功能。
- [ ] 文档中的接口路径应与代码一致。
- [ ] 文档中的字段名应与数据库设计一致。
- [ ] 文档中的 AI 流程应与实际调用方式一致。

## 12. 安全检查

完成开发前必须检查：

- [ ] 是否没有提交 API Key？
- [ ] 是否没有提交数据库密码？
- [ ] 是否没有明文保存用户密码？
- [ ] 是否没有在日志中输出敏感信息？
- [ ] 是否所有用户数据接口都做了身份校验？
- [ ] 是否所有用户数据接口都做了数据归属校验？
- [ ] 文件上传是否限制类型？
- [ ] 文件上传是否限制大小？
- [ ] 管理员接口是否有权限控制？
- [ ] AI 调用是否避免发送无关敏感数据？

## 13. 测试验证检查

任务完成前至少进行相关验证。

通用检查：

- [ ] 项目是否可以正常启动？
- [ ] 修改过的接口是否可以正常调用？
- [ ] 常见失败场景是否验证过？
- [ ] 是否没有破坏已有功能？
- [ ] 是否记录无法验证的原因？

后端 MVP 重点测试：

- [ ] 用户名为空注册失败。
- [ ] 密码为空注册失败。
- [ ] 用户名重复注册失败。
- [ ] 正常注册成功。
- [ ] 密码错误登录失败。
- [ ] 正常登录返回 Token。
- [ ] 未登录访问受保护接口返回 `401`。
- [ ] 用户只能访问自己的学习档案。
- [ ] 用户只能访问自己的会话和消息。
- [ ] AI 调用失败时返回友好错误。

## 14. 完成前检查

任务完成前必须确认：

- [ ] 本次任务目标是否完成？
- [ ] 验收标准是否满足？
- [ ] 是否只修改了必要文件？
- [ ] 是否清理了本次改动产生的冗余代码？
- [ ] 是否没有引入需求外功能？
- [ ] 是否完成必要测试或说明未测试原因？
- [ ] 是否同步更新相关文档？
- [ ] 是否说明已知风险？
- [ ] 是否说明下一步建议？
