- [x] **引用保存与恢复**：引用随对应回答保存，展示文件名、片段位置和原文，刷新后仍可查看。教材删除或不可用时明确提示，并重新检查文档归属。
- [x] **连续追问（有限问句结构）**：结合本会话最近 10 条消息中的用户问题识别“它”“那两个概念”“前者／后者”等指代，不使用 Java 或其他学科的概念名单；用明确后的问题检索当前教材，无法确定时澄清。助手历史回答不用于选择对象或替代教材证据；支持边界见 [AI-Design](AI-Design.md#rag-当前基线)。
- [ ] **失败行为**：没有证据时明确拒答，不自动切换到普通模型回答；模型失败时保留用户问题，允许重试并避免重复保存。
- [ ] **固定评测**：以 Java 集合框架教材建立 20 个带预期证据的问题，直接提问、改写、连续追问、跨片段、无答案各 4 个；另设数学、物理等跨学科补充集，避免只针对 Java 调整规则。无答案题标注预期拒答。记录教材、题目、模型和提示词版本。

此前的检索失败案例已加入回归并修复：教材同一片段写出 ArrayList 与 LinkedList 的结构描述时，“有什么区别”不再要求原文恰好出现“区别”二字。仅罗列名称、缺少一个对象或未覆盖具体属性仍不能因此放行。双方分处不同片段、复杂语义改写与未明确对象的省略问法仍需固定评测检验；不能据此认定整体检索质量已达标。

2026-09-25 至 26 跨学科修正：删除 Java 中文主题名单及只适用于英文名称的比较判定，改由共用问句解析器提取对象和所问内容。补测导数、牛顿第二定律、光合作用、机会成本、含空格的英文名称及合成概念；旧实现的 70 项相关用例中复现 18 项失败，修改后全部通过。当前后端 125 项（其中 31 项 RAG 服务、28 项追问、11 项词法检索）、前端 13 项测试及生产构建通过。独立 MySQL 的 16 组接口检查覆盖数学和物理教材、中文概念比较、歧义澄清、切换学科与会话隔离。浏览器验证数学会话刷新后追问、引用展开、切换到物理会话及“后者→它”的对象延续。测试均使用合成教材及本地确定性模型替身，没有真实模型质量结论。两处教材问答提示也改为通用表述。

仍保留的失败案例：物理教材包含瞬时速度的定义描述时，“后者有什么特点？”能正确识别对象，但因“特点”未命中而返回证据不足；继续问“它是什么？”可以召回。该案例加入后续改写评测，不把拒答误记为质量通过。复杂专名、语义改写和跨片段问题仍是限制；本轮没有新增数据库迁移，也未改动公共图谱、学习路径和练习模块的 Java 默认主题。

验收用例：

1. 在资料库问“ArrayList 和 LinkedList 有什么区别？”，切到主聊天问“经常按下标读取元素，应该选哪一种？”，仍依据同一份教材回答并显示引用。
2. 明确讨论 ArrayList 后追问“那它有什么缺点？”，结合本会话理解；上下文不足或对象不明确时先澄清。
3. 刷新页面、重新打开会话后，教材选择和历史回答的引用仍能恢复。
4. 教材中没有答案时拒答；切换用户或伪造文档 ID 时不能取得他人教材、历史或引用。
5. 固定 20 题逐题记录检索前 4 段是否包含预期证据、回答是否受引用支持、拒答是否正确，以及耗时；失败项修复并复测后才能勾选完成。额外覆盖超时和重试。

现有 31 项 RAG 服务、28 项指代解析及 11 项词法检索自动测试应继续通过；服务单测隔离了模型和数据库，不能代替真实教材与浏览器验收。

## 阶段 2：形成教学闭环

- [ ] 将意图、知识图谱上下文和教学策略计算移到回答生成前，将策略约束传给同一次模型调用；页面标签、记录的策略和实际请求保持一致。
- [ ] 明确诊断、讲解、理解检查、练习、反馈的进入条件，由代码控制状态迁移，不能只因用户说了关键词就宣布已学会。
- [ ] 练习对应本次知识点、教材证据和暴露出的错误；答错后补讲或补前置知识，再用不同题目检查。
- [ ] 保存当前步骤，退出后可以继续；失败重试不丢失已完成步骤。

验收：用 ArrayList 索引访问、HashMap 键唯一性两个知识点各走通一次完整流程，分别验证答对、答错、回答模糊和中途退出。自动测试确认策略在模型调用前确定并进入请求；人工检查教学内容是否遵循策略。

## 阶段 3：让学习记录有依据

- [ ] 为答题、教学评价和复习结果保存可追溯证据，区分客观判分与模型评价；展示可理解的学习状态及依据。
- [ ] 修正掌握度只取历史最大值的逻辑，明确新证据、近期错误和时间间隔如何影响状态；不将工程分数宣传为精确教育测量。
- [ ] 根据薄弱点生成可保存、可完成的复习任务，并将完成结果反馈到知识点状态。
- [ ] 同一答案重复提交不重复计分；模型评价失败或证据不足时，不错误提高掌握状态。

验收：同一知识点先答对后答错，能看到有依据的状态调整和复习建议；重复提交不产生重复增益；复习后能追溯变化所依据的题目、时间和结果。

## 阶段 4：验证实际效果

- [ ] 先选定 Java 集合框架的少量主题、学习任务和评价题，再开展小范围试用，保留初始诊断、即时检查和延后复习记录。
- [ ] 记录任务完成情况、提示次数、引用错误、错误反馈、复习表现和用户卡住的位置，保留失败案例。
- [ ] 比较普通聊天与本系统时，使用可比较的教材和题目，记录提示、模型及版本差异；不能把一次答对或聊天时长当作学习效果证明。
- [ ] 形成一次评测结论和按影响排序的问题列表，结论限于本次样本和任务范围，不直接声称优于通用模型。

验收：能解释哪些任务有效、哪些失败、判断依据是什么，并将高影响问题回填到前述阶段。具体评测材料随代码保存，整体结论与进度仍汇总到本文。

## 阶段 5：按结果评估架构升级

以下均为候选方案，当前未实现，不纳入首版必做范围：

- 词法检索不足时，对照评估 embedding、混合检索和重排，比较召回、引用支持、拒答、时延和成本，再选择存储与模型。
- 流程复杂度有实际需要时，评估 Python 单 Agent / LangGraph。Java 继续负责身份、文档所有权、事务、最终写入和对外 API，Python 不绕过 Java 修改业务数据。
- 新服务先定义请求、响应、错误与版本契约，并实现超时、重试上限、调用预算、请求关联和回退。此前提出的 5 次模型调用、3 个工具步骤、单次 10 秒、总计 20 秒和重试 1 次仅为候选试验初值，必须经实际评测确定。
- 单 Agent 经对照验证仍不足时，才考虑有限 Multi-Agent。SSE、容器部署、外部队列和任务恢复按交付需要单独评估。

验收：使用同一题集和任务比较当前版本与候选版本，记录收益及退化；故障时能回退，权限和数据一致性不变。没有收益时保留当前架构，不必采用所有候选技术。

## 贯穿各阶段的约束

- 不提交 `.env`、密钥、数据库密码、上传资料、日志和构建缓存。曾出现在压缩包或日志中的真实凭据仍需轮换，未核验前不记录为完成；公开部署显式配置生产凭据。
- 文档、会话、记忆、图谱和引用始终按当前用户检查所有权；模型输出和教材内容不能替代权限判断。
- 上传解析限制、提示注入隔离、日志脱敏、模型超时和任务中断恢复纳入对应功能的验证。
- 完成任务后更新勾选项和验证记录；范围、接口、数据库变化更新对应现有文档，不另建重复的总体规划。

需要手工浏览器验收时可附加 `--hold-for-browser`。脚本完成接口检查后，在输出目录写入 `browser-fixture.json`，其中包含仅用于临时环境的账号、API 地址和结束标记路径；让测试前端代理该 API 后进行操作。完成后创建指定结束标记，脚本即清理临时服务和数据库；最迟 30 分钟自动清理。该文件含临时口令，不提交到仓库。
