## 根因与下一步

1. **搜索动作与检索接口不匹配。** 模型输出“导数 定义”“青栈标记 提出者”等关键词串，现有 `RagQuestionParser`／`RagKeywordScorer` 会按完整对象名称或属性约束解释。11 条实际生成的搜索动作（含被护栏拦下、未执行的动作）用生产评分器离线回放，所有片段得分均为 0；真正发生的 7 次搜索回调也均返回空证据。Java 基线还先拆分复合问题，Agent 回调直接对合并查询评分，因此不能仅凭共用评分器就认为检索行为相同。
2. **规划过早要求澄清。** A03 的历史已明确指向导数；A06、A08 的专有名词可在所选教材中检索，但 Agent 在读取证据前就终止。应先检索明确对象，区分资料缺失和真正的指代歧义。
3. **停止原因的提示过于笼统。** A01、A02、A05 在只剩最终复核槽位时仍要求搜索；A04 则重复同一查询，在第 2 次模型调用后被去重拦下。它们均显示“调用额度已用完”，不表示本轮 40 次授权已用尽。下一轮应明确重复查询、工具上限与模型预算的不同原因。

后续先修复搜索输入契约、复用子问题检索逻辑及澄清条件，用本次原始模型动作回放验证，再冻结新版本进行真实复测。不能通过增加模型次数解决零命中，也不应放松引用或权限校验来换取通过率。本次仅诊断和记录，生产代码、提示、限制均未修改。

## 方法与边界

- [题集与标准](stage5-agent-cases.json)在首个真实调用前冻结。8 题是同一编码助手在看过前期检索实验后设计的合成工程案例，不是独立留出集、随机样本或真实学习效果试验。
- 两个独立 Java 实例共用本次临时库中的同一用户和教材；各题、各路径使用不同会话。两边使用相同供应商与模型，保留各自生产提示和输出格式，每题交替执行顺序。
- 精确片段直接写入隔离库，**没有覆盖上传分片**；历史只包含预先写入的用户问题，无准备阶段模型调用。更长真实资料、完整问答历史、多次重复、负载和独立专家审阅仍待验证。
- Java 每题最多 1 次、全组最多 8 次；Python 每题最多 4 次、全组最多 32 次。统一转发层先同步落盘、再发模型请求，用排他锁防止并行重复运行。重启、换输出目录不会清空本轮授权账本，已开始的题组不能自动重放。
- 编码助手逐条阅读所有应用结果、来源和 21 条原始模型响应，按冻结标准人工判定；不是服务模型自评，也不是盲审或独立人类评审。失败保留在分母中。
- 已完成 110 项脚本测试及完整本地演练。演练初期修复的是评测层健康检查转发和替身的空检索处理；未据此调整生产提示。真实调用前后核对应用、题集和执行脚本指纹一致。
- 随机临时数据库已删除，三个测试服务均已停止；原学习库和普通启动配置未修改。本轮没有应用源码或接口改动，未重复 Java／前端构建或浏览器验收，先前工程验证范围见[开发记录](../../docs/Development.md)。
